# Shared Connections: consent and agent access

Task 3 adds a private Crew bridge to canonical Connections storage. Native Pilot work, subscription and heartbeat records are not prerequisites. Gmail and Patty KB are personal resources for this first release; workspace human credentials are rejected.

## Private wire contract

`POST /api/connection-workspaces/:bindingId/manage` accepts exactly `{schema:"crew.connections-manage/v1", token, control}`. `control` is the original signed UTF-8 `crew.connections-control/v1` JSON string, not a reserialization. The service hashes that string and introspects current Crew authority for the exact operation, binding and digest. It supports catalog, availability, personal inventory/create/authorize/disconnect, access list/grant/revoke/request/request-resolve. Workspace creation is explicitly denied.

`POST /api/connection-workspaces/:bindingId/oauth-complete` accepts exactly `{schema:"crew.connections-oauth-complete/v1", token, callback}`. `callback` is the original signed `crew.connection-oauth-callback/v1` JSON string with state and either code or the bounded provider-error variant. The hash covers that string only. Both callback variants permit optional `iss` from the two pinned issuers. Before claiming state or exchanging code, the service compares it to the actual resource app: KB requires exactly `https://login.patty.io/realms/internal`; Gmail accepts absent or exactly `https://accounts.google.com`. Wrong issuer never consumes state. The issuer remains ephemeral and digest-bound. Body/query errors terminate inside the private router with no-store and no-referrer headers, before native body logging, sessions or subscription middleware. Task 4 owns the Crew browser landing and native handoff. Production must additionally qualify private networking, TLS, proxy/access-log redaction and callback URL handling.

Operation results use the frozen `crew.connections-result/v1` safe metadata fields. No native connection object, credential reference, code, state, token, provider payload or unencrypted authorization URL enters the operation journal. The owner-private authorization URL is reconstructed from canonical state for exact-intent retries. New operations serialize under the binding row, and the mutation and durable receipt commit together. Replays still require fresh current authority; another intent using the same caller request UUID conflicts. Database lock and statement deadlines bound the publication transactions.

## Storage and consent lifecycle

`connection_availability` records admin approval of an app and read/search actions. `connection_resources` binds a canonical connection and user consent to one workspace and immutable owner account. `connection_agent_access` pins the managed agent public key, actions, consent ID and consent generation. `connection_approval_requests` contains only safe approval metadata. `connection_operations` is the durable metadata-only exact-intent journal.

Canonical `connection_grants(kind=user, subject_user_id=verified Accounts account)` remains the consent record. OAuth state remains solely in `tool_oauth_states`, including persisted redirect, workspace, operation and consent generation. Callback validates owner and exact redirect before atomic DELETE RETURNING; an incorrect owner/context cannot consume it. Token exchange and KB signature validation occur outside publication locks. Publication then locks the binding and validates enabled availability, current authority expiry, owner, canonical consent status and exact generation before writing the canonical user vault and grant in one transaction. Disconnect or reauthorize increments generation. An old agent grant never follows new consent automatically; regrant is required.

Personal access and refresh tokens use canonical user secret definitions and user values, never company-scope token values. Native personal reconnect replaces legacy company-scope token references without rotating or reusing those values. Provider client secrets remain operator/company-scoped. Native APIs cannot resolve external connections, the native token broker denies them, and native policy denies them even if ordinary profiles would allow access. Shared operations create no native agents, issues, heartbeat runs or work subscriptions.

The trusted operator `provisionConnectionWorkspace` helper atomically reserves an exact Accounts organization/company/workspace/community/authority mapping, disabled by default. Conflicting identity reuse fails. Both organization reservations and enabled/disabled workspace bindings block native company deletion through friendly preflight and restrictive foreign keys. Native company archive does not mutate external availability or consent.

## Operator registration and live gates

`connection_provider_registrations` is operator-owned with no public mutation route. Its safe metadata shape is `binding_id`, `app_id`, `client_id`, optional `client_secret_id` (a canonical reference, never a value), `redirect_uri`, optional `audience`, and `qualified` (default false). A readiness row does not prove registration or live acceptance. A supplied client-secret reference must identify an active company-scope local-encrypted secret in the exact bound company; Gmail requires it. This keeps remote secret-provider I/O out of the consent transaction. Existing ambient desktop/device credentials and OAuth environment values are never used for these external connections.

The only callback is `https://<bound Crew origin>/api/connections/oauth/callback`, derived from the authority origin and compared exactly. Registration changes invalidate outstanding consent retries/callbacks; a new consent operation adopts the new registration. Provider endpoints and scopes are fixed server-side. No user-selected transport, URL, command, environment, header, client or dynamic client registration is supported.

Gmail uses `https://accounts.google.com/o/oauth2/v2/auth`, `https://oauth2.googleapis.com/token`, `https://gmail.googleapis.com`, and only `https://www.googleapis.com/auth/gmail.readonly`. Server consent requests PKCE, offline access and explicit consent. A refresh token being requested or stored does not prove successful renewal.

Patty KB uses the internal realm `https://login.patty.io/realms/internal`, its fixed authorization/token/JWKS endpoints, `https://mcp.kb.patty.io/mcp`, and `mcp:tools`. The registration audience is the exact deployed token audience, not inferred from the MCP resource URL. The verifier requires RS256 with a pinned-issuer JWKS signature, exact issuer, client `azp`, configured audience, current expiry/nbf, `mcp:tools`, and immutable subject. Successful owner-bound OAuth records `providerTenant={name:issuer,externalId:sub}` on canonical consent; email strings never establish identity. `mcp:tools` permits more upstream capabilities, so Task 5 must enforce the actual discovered read-only tool allowlist and real per-user page ACLs. No live Google registration, KB user consent, tools discovery, ACL enforcement or revoke propagation acceptance is claimed here.

All authority, token and JWKS requests use an explicit direct HTTPS agent with certificate validation, redirect rejection, a 5-second full-response deadline, and bounded request/response bodies. Ambient proxy environment, global fetch and global HTTPS agents do not select the route. Tests use local trusted TLS and poisoned globals; production route/CNI qualification remains separate.

## Task 5 internal refresh handoff

This task does not expose shared tool execution or automatic refresh. Until the latter is implemented, Task 5 must deny expired access credentials. Connect-once renewal is a remaining first-release acceptance gate.

Resolve `connection_resources.consent_id` to canonical `connection_grants`; credential refs with `configPath=oauth.access_token` and `oauth.refresh_token` remain private internal references. Resolve the exact user value through `secretService.resolveUserSecretValue` and its canonical owner/definition guards, never `resolveSecretValue` for a company credential. A controlled adapter must preserve declaration enforcement or use the existing deliberate owner-scoped internal resolution pattern; it must not create native run identity to bypass it.

Reuse the canonical token exchange/refresh parsing and user vault methods in `tool-access.ts` / `secrets.ts`. The existing native `refreshOAuthCredentials` is company-credential oriented and remains unchanged. Shared refresh must add the same binding/availability/consent generation/revoke and authority-expiry fence around transactional user-vault publication, with provider I/O outside the lock. Preserve the verified KB issuer/sub association across refresh; reject changed subject, issuer, client or audience. Handle unknown rotating-refresh outcomes by requiring reauthorization rather than replaying a potentially consumed refresh token. No public endpoint should return tokens or secret refs.

## Migrations and validation

Generated migrations 0003 and 0004 add this storage, canonical state/generation fields and restrictive/composite foreign keys. Drizzle emitted 0004 foreign keys before their referenced unique constraints; its generated statements were reordered so prerequisites precede dependents. Disposable embedded Postgres tests apply the normal migration chain. Existing deployed OAuth state rows without a saved redirect fail closed and require restarting consent.

Focused receipts and the exact incremental source manifest are in the Crew SDD Task 3 report. Broad stable-branch verification, provider registration, deployment and real acceptance remain separate controller gates.

The browser landing normalization is Task 4: ignore bounded unknown provider display parameters while rejecting duplicate core security parameters and code/error mixtures; forward only state/code-or-error/iss in the strict signed body. This follows [RFC 6749 section 4.1.2](https://datatracker.ietf.org/doc/html/rfc6749#section-4.1.2) and [RFC 9207 issuer validation](https://datatracker.ietf.org/doc/html/rfc9207#section-2.4).
