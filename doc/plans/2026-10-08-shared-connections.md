# Shared Connections authority foundation

Date: 2026-10-08
Scope: PAT-3470 Task 1, shared external workspace authority contract.

Apps v2 remains the resource authority. The existing company ID is a storage
namespace for connections; Crew-only use does not require a Pilot subscription
or create Pilot work records. This deliberately extends the resource identity
boundary while preserving Pilot's task-centered product and native run-bound
authorization. Crew's chat model remains outside the core Pilot work model.

> Sign-in tokens are never reused as resource tokens; id.pilot.test never
> stores resource tokens; no connections hub on the ID service.

## Storage and operator lifecycle

`connection_workspace_bindings` stores UUID `id`, company foreign key
`companyId`, bounded immutable `accountsOrganizationId`, UUID `workspaceId` and
`communityId`, `authorityUrl`, disabled-by-default `enabled`, and timestamps.
The global composite unique key `(workspaceId, communityId)` prevents a Crew
context from mapping to multiple company namespaces or Accounts organizations.
Disabled rows reserve that mapping. `(companyId, id)` is additionally unique for
company-scoped references by subsequent connection/grant tables. Company deletion
cascades bindings. SQL checks reject blank/overlong organizations and non-HTTPS,
credential-bearing or non-introspection endpoint shapes; the resolver additionally
requires a fully canonical endpoint.

`connection_organization_bindings` has `companyId` as primary key and company
foreign key, unique bounded `accountsOrganizationId`, timestamps, and a unique
composite `(companyId, accountsOrganizationId)` reference key. Each workspace
binding has a composite foreign key to this exact company/organization pair.
The database therefore enforces one organization per shared namespace and one
namespace per organization under concurrency. Several workspaces of that same
organization may share the namespace. Native Pilot companies may omit the
organization row entirely; the companies table and native authorization are
unchanged. Organization deletion cascades its external workspace bindings.

Migration `0001_futuristic_phil_sheldon.sql` is generated by `pnpm db:generate`
against the existing squashed `0000_rare_thunderbird` baseline. It adds only the
new table, foreign key, checks and indexes, with the normal snapshot and journal
entry. No migration is applied to an operator's instance by this task.
After the organization-scope clarification, normal generation additionally
produced `0002_confused_the_watchers.sql` for the organization table and composite
foreign key. Both are additive task-local migrations; the preexisting baseline
is preserved. The intermediate workspace-only migration has never been deployed.

Provisioning and rebinding remain operator-owned. Verify the exact immutable
Accounts organization and Crew workspace/community plus trusted TLS endpoint,
disable before changing a mapping, update `updatedAt`, verify the issuer wiring,
and enable only when downstream resource gates are ready. There is no member
write or activation API in this foundation.

## Exact service and wire contract

```ts
connectionAuthorityService(db: Db, options?: { fetch?: typeof fetch }): {
  resolveConnectionAuthority(input: ResolveConnectionAuthorityInput):
    Promise<ResolvedConnectionAuthority>
}

type ResolveConnectionAuthorityInput =
  | { bindingId: string; token: string; purpose: "management";
      action: string; requestDigest: string }
  | { bindingId: string; token: string; purpose: "execution"; action: string };

interface ResolvedConnectionAuthority {
  binding: ConnectionWorkspaceBinding;
  context: ConnectionManagementContext | ConnectionExecutionContext;
}
```

The optional fetch adapter is for controlled tests; production uses platform
HTTPS fetch. Binding lookup always uses actual Drizzle storage. No caller-supplied
lookup, authority URL or identity is accepted. The stored binding supplies the
only company namespace returned to downstream services.

POST only to the exact persisted `/api/connections/introspect` URL. Request JSON:

```json
{ "schema": "crew.connection-introspection/v1", "token": "opaque-capability" }
```

The token alone carries issuer-verified purpose and management operation.
Pilot's requested purpose/action/digest are local expectations, not fields
forwarded for the relay to treat as authority. The token is opaque, never
decoded as a model or native Pilot credential by this resolver. Those token
classes must receive a denied verdict from the purpose-specific trusted issuer.

Response JSON is strict, with no additional fields:

```ts
{ schema: "crew.connection-authority/v1", valid: true, context }
```

Every context includes:

- `schema`, `audience: "patty.connections"`;
- `accountsOrganizationId`, `workspaceId`, `communityId`;
- `requesterAccountId`, `requesterPubkey`;
- `issuedAt`, `expiresAt` as safe integer UTC seconds.

Management schema `crew.connection-management/v1` additionally includes
`role: "owner"|"admin"|"member"`, `requestId`, `action`, `requestDigest`.
Execution schema `crew.connection-execution/v1` additionally includes
`agentPubkey`, `enrollmentId`, `generation`, `channelId`, `conversationId`,
`turnId`, `sourceMemberAccountIds`, `audienceAccountIds`. Execution generation is
a positive safe integer: generation zero is pre-start custody, not an active
turn. Conversation is an opaque bounded `channel:`/`thread:` identity. No
synthetic native Pilot identity or database foreign key is used for these Crew
agent/turn identities.

All immutable text IDs have 1–256 characters, without whitespace/control
characters or normalization. Organization may be `org_<hex>`; it is not assumed
to be a UUID. Workspace, community, enrollment, channel and turn are lowercase
UUIDs. Pubkeys, request ID and digest are 64 lowercase hex. Action is 1–128
characters matching `[a-z][a-z0-9._:-]*`. Each account array has 1–100 unique
immutable entries; oversized lists deny rather than truncate. Opaque tokens have
1–4096 characters and the serialized request must also fit 16 KiB.

Only `valid: true` with a matching strict purpose-specific context is accepted.
Scope fields must match the stored binding exactly. Management action and digest
must match the requested operation. The lifetime must be positive and at most
60 seconds, with `issuedAt <= now < expiresAt` at return. The resolver re-reads
the binding after introspection and rejects disable/rebinding during the call.
It has no positive cache. Current membership, enrollment, generation and source
authority are the trusted relay's responsibility on every introspection.

## Transport and downstream boundaries

HTTPS only, no credentials/query/fragment, fixed canonical path. Redirects are
refused with `redirect: "error"`; unexpected response URL or redirect metadata
also denies. POST is marked no-store. Request size is at most 16 KiB, streaming
response at most 64 KiB, and the request including response body has a five-second
budget. Abort or size excess cancels the body. Errors use generic 403
`connection_authority_denied` or 503 `connection_authority_unavailable`, without
raw token, provider body or transport details. Tokens and payloads are never
persisted or written to activity records here.

Authority identity is a prerequisite, not a resource grant. Later tasks must
check current application availability, owner consent, connection state,
agent/resource/action grants, approved tool catalog and exact result audience.
Personal reads/search go only to their owner in the first release. Member role
does not permit admin actions. Execution actions remain exact downstream broker
policy decisions. Existing OAuth/PKCE, canonical consent, encrypted vault and
native Pilot authorization must be reused.

## Validation and remaining gates

Focused shared-schema and actual embedded PostgreSQL resolver tests exercise
strict purposes, scope/action/digest mismatch, missing/disabled binding,
revocation between calls and in flight, expiry/future issuance/overlong lifetime,
malformed/native contexts, bounded bodies, timeout, and redirects/unavailability.
Storage tests exercise disabled defaults, unique scope, cascading deletion,
same-organization multi-workspace acceptance, cross-organization/company
rejection, and concurrent namespace insert serialization.
The migration and repository typecheck use the standard database workflow.
Full verification results are recorded in the controller's Task 1 report.

No issuer endpoint, signed Nostr management route, operator provisioning UI,
application/agent grant schema, OAuth adaptation, broker integration or provider
registration is supplied by Task 1. Controlled tests do not qualify deployed TLS,
live Google consent, private KB ACLs, native desktop behavior or production
promotion. Those remain explicit later-task and live acceptance gates.
